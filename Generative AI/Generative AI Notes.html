01
The Problem: Why AI Exists
Some problems cannot be solved by writing rules

In traditional programming (JavaScript, Java, C, C++, Python), you write the rules. The computer follows them exactly.

Traditional programming
Data + Rules (written by you)  →  Answer

This works well when you can describe the rules: calculate GST, check a password, sort a list.

Now try this: is this image a cat?

To a program, an image is only a grid of numbers (pixel values). Try writing the if/else:

  • "If it has pointy ears" → dogs and foxes also have them.
  • "If it has whiskers and fur" → what if the cat is sleeping, half hidden, black on a dark sofa, or a cartoon?

The possible images are endless, so the rules never finish. The honest answer is: we know a cat when we see one, but we cannot write down how.

Watch the rules fail, then watch ML solve it

Traditional programming
Machine learning
Key Concept

Traditional programming is not "unable" to compute this. The problem is that no human can write the rules by hand. So we flip the approach: give the computer examples and let it find the rules itself. That is Machine Learning.

How machine learning solves it

Collect data
Thousands of images: cats and not-cats.
Label the data
Each image gets a tag: "cat" or "not cat". This is called a labeled dataset.
Train
A learning algorithm looks at the examples again and again, adjusting its internal numbers (parameters / weights) each time it guesses wrong.
You get a model
The trained result is an ML model. Give it a new image it has never seen and it answers "cat: 97%". Using a trained model like this is called inference.
Machine learning
Data + Answers (labels)  →  Rules (the model)

Correct terms to use

Everyday wordsCorrect termMeaning
Tagging the imagesLabelingAttaching the right answer to each example.
Learning from tagged examplesSupervised learningTraining where every example comes with its answer.
Cat or not catClassificationPutting an input into one of a fixed set of categories.
The numbers inside the modelParameters / weightsWhat actually changes during training.
Using the model after trainingInferenceSending input, getting a prediction. No learning happens here.

What these models could do

For years, ML mostly gave us two things:

  • Classify: cat or not, spam or not spam, fraud or genuine.
  • Predict: which video you will watch next on YouTube, which show on Netflix, which song on Spotify (recommendation systems), or tomorrow's price or demand.

Notice what is missing. These models pick from options that already exist. They choose a label or a number. They do not create a new paragraph, a new image or new code.

02
What Is Generative AI?
From choosing an answer to creating new content
Definition

Generative AI is AI that creates new content (text, code, images, audio, video) instead of only labeling or scoring existing content. It learns the patterns in its training data and produces new output that follows those patterns.

Earlier ML (predictive)Generative AI
Question it answers"Which one is it?" / "What number?""Make me a new one"
OutputA label or a numberA paragraph, an image, a function
Training dataMostly labeled by humansHuge amounts of raw, unlabeled data
ScopeOne model, one narrow taskOne model, many tasks
ExamplesSpam filter, YouTube recommendationsChatGPT, Claude, Gemini, Midjourney

Where it sits in the family

These words are not competitors. Each one is a smaller box inside the previous one.

Artificial Intelligence
Any technique that makes a machine act intelligently
Machine Learning
Learns rules from data instead of being hand-coded
Deep Learning
ML using neural networks with many layers
Generative AI
Deep learning models that create new content
LLMs
Generative models for text and code
💡

Two common mix-ups. Deep learning is a part of machine learning, not a separate branch next to it. And the cat classifier is already deep learning in practice: modern image classifiers are deep neural networks. So deep learning did not arrive with LLMs. What arrived was a new network design (the Transformer, 2017), a new way of training without human labels, and a huge jump in scale.

Generative AI is also wider than text. Image generators, voice generators and video generators are generative AI too. The LLM is the text member of the family, and it is the one we build with in this course.

03
Large Language Models and Tokens
What an LLM is, how it is trained, and the unit it works in
Definition

A Large Language Model (LLM) is a very large neural network trained on a huge amount of text to do one job: predict the next token. Everything it appears to do (answer, translate, write code) comes from doing that one job extremely well.

How do we get from a cat classifier to an LLM?

Three things changed.

What changedBeforeFor LLMs
DataThousands to millions of hand-labeled examplesA large share of the public internet, books and code. Trillions of words.
LabelsHumans tag every exampleNo human labeling. Hide the next word and ask the model to guess it; the text itself is the answer key. This is self-supervised learning.
ComputeA few GPUsThousands to lakhs of GPUs running for weeks or months.
ArchitectureNetworks built for one taskThe Transformer, which can look at all the words in the input together and scales well.

"Large" refers to the number of parameters: billions of them. A small local model has 1 to 8 billion; frontier models have far more.

💡

Precision check: we say "trained on all the data in the world" loosely. It is really a very large slice of public text, not literally everything, and never your private data unless someone puts it there.

How an LLM actually produces text

An LLM never writes a whole answer in one go. It produces one token, adds it to the text, and runs again. Step through the full journey of one answer:

Text
Tokens
Transformer
Chances
Sampling
Append

The same loop in words

StepNameWhat happens
1TokenizationThe input text is cut into tokens, and each token becomes a number (token ID).
2Forward passAll the token IDs go through the Transformer (the neural network inside the LLM) together, in one run. It looks at every token at once to work out how they relate. The weights do not change; nothing is learned here.
3ProbabilitiesThe model outputs a chance for every token in its vocabulary to be the next one.
4SamplingOne token is picked according to those chances. Likely tokens win most of the time, not every time.
5AppendThe picked token is added to the end of the text.
6RepeatThe longer text goes back in as input. Generating like this, one token at a time from its own output, is called autoregressive generation.
Key Concept

An LLM is still a prediction model, exactly like Section 1. It predicts the next token. Generation is that prediction run in a loop. And because step 4 is a pick with some randomness, the same prompt can give different answers. Section 5 shows how to control that pick.

How does it know when to stop?

The loop could run forever. Three things end it:

Stop reasonWho decidesWhat happens
End tokenThe modelThe vocabulary has a special token that means "I am done" (called the end-of-sequence or EOS token). In training, every document and every reply ended with it, so the model learned where answers end. When this token is sampled, generation stops. It is never shown to the user. This is the normal, healthy way to stop.
max_tokensYouYou set a limit on output length. If the model reaches it before producing the end token, the answer is cut off, often mid-sentence.
Stop sequenceYouYou give a string (for example "###"). Generation halts the moment the model writes it.
💡

Check the stop reason in your code. Every API response tells you why it stopped: a value like stop (finished naturally) or length (hit the limit). If you see length, the answer is incomplete.

What is a token?

The model does not read letters or words. Text is first cut into tokens: small pieces that can be a word, part of a word, a space or a symbol. Each token maps to a number, and the model only ever sees those numbers.

"Tokenization is fun!" → [Token] [ization] [ is] [ fun] [!] → 5 tokens
  • Rule of thumb for English: 1 token ≈ 4 characters ≈ ¾ of a word. 100 tokens is about 75 words.
  • Hindi, Hinglish, code and rare words usually take more tokens than plain English.
  • Every model family has its own tokenizer, so the same text gives different counts on different models.

Why tokens matter to a developer

Because of tokensWhat it means for you
CostAPIs bill per token. Input tokens and output tokens are priced separately, and output is usually more expensive.
LimitsEvery model has a context window: the maximum tokens it can handle in one request, input and output together.
SpeedOutput is produced one token at a time, so a longer answer takes longer.
⚠️

An LLM does not look up facts. It produces the most likely next tokens. Most of the time that is correct; sometimes it is fluent and wrong. This is called hallucination. Never trust an LLM answer blindly where correctness matters.

04
Three Ways to Use an LLM
Local, self-hosted on the cloud, or through an API

A trained model is a large file of weights. To use it, something has to load that file onto hardware and run inference. The only question is: whose hardware?

Way 1 — Local

Run the model on your own machine

Install a tool like Ollama (or LM Studio), download an open-weight model (Llama, Gemma, Qwen, Mistral), and run it on your laptop.

Terminal
# download the model and start chatting
ollama run llama3.2

# Ollama also exposes a local API on port 11434
curl http://localhost:11434/api/generate -d '{"model":"llama3.2","prompt":"Hello","stream":false}'

Benefits

  • Free to run, no per-token bill
  • Fully private: data never leaves your machine
  • Works offline
  • No rate limits; great for learning and experiments

Drawbacks and pitfalls

  • Limited by your RAM / GPU, so only small models fit
  • Small models are noticeably weaker than frontier models
  • Slow on a normal laptop
  • It runs only on your machine. Your deployed app cannot call your laptop.
💡

Rough sizing: 8 GB RAM handles models around 3 to 4 billion parameters; 16 GB handles around 7 to 8 billion. Bigger than that needs a serious GPU.

Way 2 — Host

Rent a GPU machine on the cloud and run the model there

Rent a GPU server (AWS, GCP, Azure, RunPod and similar), load an open-weight model with a serving tool like vLLM or Ollama, and expose your own inference endpoint. Your app calls your server.

Benefits

  • You control the data: it stays in your cloud account
  • You choose the model, version and any fine-tuned variant
  • No vendor rate limits; you scale it yourself
  • Can be cheaper than an API at very high, steady volume

Drawbacks and pitfalls

  • You pay per hour whether anyone uses it or not
  • GPUs are expensive and sometimes hard to get
  • You own the DevOps: scaling, monitoring, updates, security
  • Only open-weight models; the best closed models are not available
  • Forgetting to shut a GPU instance down is a costly mistake
Way 3 — API

Call a provider's model and pay as you use

A provider (OpenAI, Anthropic, Google, Mistral and others) runs the model on their hardware. You send an HTTP request with your API key and pay for the tokens you use.

index.js
import { ChatMistralAI } from "@langchain/mistralai";

// reads MISTRAL_API_KEY from the environment
const model = new ChatMistralAI({ model: "mistral-small-latest" });

const res = await model.invoke("Explain tokens in one line");
console.log(res.content);

Benefits

  • Access to the strongest models available
  • Zero infrastructure; working in minutes
  • Pay only for what you use; idle costs nothing
  • Scaling and reliability are the provider's job

Drawbacks and pitfalls

  • Your data goes to a third party (check their data policy)
  • Cost grows with usage; a bug in a loop can burn money fast
  • Rate limits and occasional outages you cannot fix
  • Models get updated or retired, which can change your app's behaviour
  • A leaked API key is someone else spending your money
⚠️

Never put an API key in frontend code or push it to GitHub. Keep it in .env on the server, call the LLM from your backend, and set a spending limit in the provider dashboard.

Side by side

WhatLocalHostAPI
You pay forNothing (your own hardware)GPU hours, used or idleTokens used
Setup effortLowHighLowest
Model qualitySmall open modelsLarge open modelsBest available
Data privacyStays on your machineStays in your cloudGoes to the provider
ScalingNot possibleYou manage itProvider manages it
Best forLearning, offline, private experimentsStrict data rules, high steady volumeAlmost every product, especially early
Which one do we actually use?

The API. Most real products start here and many stay here, because you get the best models with no infrastructure and no idle cost. Use local to learn and experiment for free. Move to hosting only when you have a real reason: data that legally cannot leave your systems, or volume so high and steady that renting GPUs is cheaper than paying per token.

Inference Parameters
Temperature, Top-K, Top-P and thinking

From Section 3: the model outputs a chance for every token, and then one token is picked (sampling). These parameters change the list of chances before the pick. They always run in this order:

Model's chances for the next token
  ↓ 1. Temperature reshapes the chances
  ↓ 2. Top-K removes tokens by position (keep the first K)
  ↓ 3. Top-P removes tokens by running total (keep until the total reaches P)
  ↓ 4. The tokens that are left are rescaled so their chances add up to 100%
  ↓ 5. One token is picked

One example is used for everything below. The prompt is "The sky is ___" and the model gives these chances, sorted from most to least likely:

blue 56.5% · clear 17.0% · dark 10.3% · cloudy 7.6% · grey 5.1% · falling 1.9% · green 1.3% · pizza 0.2%
1 — Temperature

Temperature: how risky is the pick?

Temperature stretches or flattens the chances. It removes nothing.

TokenTemperature 0.2Temperature 1.0Temperature 2.0
blue99.7%56.5%32.9%
clear0.2%17.0%18.0%
pizza0.0%0.2%2.1%
ResultAlmost always "blue". Same answer every time.The model's own chances, unchanged.Chances move closer together. Odd words get picked.
  • Low (near 0): the leader gets even further ahead. Focused and repeatable.
  • High (above 1): the gap shrinks. More variety, more risk of nonsense.
  • Exactly 0: no randomness at all. Always the top token.
2 — Top-K

Top-K: keep only the first K tokens

Count K tokens from the top of the list. Everything after that is removed, whatever its chance.

Top-K = 3
blue ✓   clear ✓   dark ✓  | cloudy ✗   grey ✗   falling ✗   green ✗   pizza ✗

K is a count. K = 1 means only the top token (same as temperature 0). A typical value is 40.

3 — Top-P

Top-P: keep tokens until their chances add up to P

Start at the top and keep a running total. Add tokens one by one. The moment the total reaches P, stop. The token that crosses the line is kept; everything after it is removed.

Top-P = 0.80 (80%)
blue  56.5% → running total 56.5%  — under 80%, keep going
clear 17.0% → running total 73.5%  — under 80%, keep going
dark  10.3% → running total 83.8%  — crossed 80%, keep this one and stop
cloudy, grey, falling, green, pizza → removed

P is a total, not a count. Here it kept 3 tokens, but that number changes with the situation.

4 — Rescale

Why the final numbers look different

After the cut, the three tokens left add up to 83.8%, not 100%. A pick needs chances that total 100%, so each one is divided by 83.8%:

blue  56.5 ÷ 83.8 = 67.4%
clear 17.0 ÷ 83.8 = 20.3%
dark  10.3 ÷ 83.8 = 12.3%   → total 100%
💡

So there are two sets of numbers. The chances used to decide the cut (they add up to roughly P), and the final chances used for the pick (always 100%). Top-P 0.80 does not mean the final numbers add to 80%.

Top-K vs Top-P

SituationTop-K = 3Top-P = 0.80
Model is sure
("The capital of India is New ___": Delhi 96%)		Still keeps 3 tokens, including two poor onesKeeps 1 token. Delhi alone crosses 80%.
Model is unsure
(ten tokens near 8% each)		Keeps only 3, throws away good optionsKeeps all ten, since it needs that many to reach 80%

Top-K is a fixed cut. Top-P adapts to how confident the model is, which is why it is the more commonly used of the two.

Try it yourself

Prompt: "The sky is ___"
TokenChance after temperatureRunning totalStatusFinal chance
Picked so far: nothing yet

Read the table left to right: temperature sets the chance, the running total decides the Top-P cut, and the last column is what the pick actually uses. Press "Sample a token" several times to see the final chances in action.

Two more controls

ParameterWhat it does
max_tokensHard limit on output length. Protects cost. If it is too low the answer is cut off mid-sentence (stop reason length).
stopStop sequences: strings that end generation as soon as the model writes them.

What to set

TaskTemperatureWhy
Data extraction, JSON, classification, code0 – 0.2You want the same correct answer every time
Chatbot, explanations, summaries0.3 – 0.7Natural but still reliable
Brainstorming, stories, marketing copy0.8 – 1.0Variety is the goal
💡

Change one knob at a time. Adjust temperature or top_p, not both together. Also, not every provider exposes every parameter: for example, some APIs do not offer top_k at all.

⚠️

Temperature 0 does not mean "correct". It means "most likely and repeatable". A model can be confidently wrong at temperature 0. And high temperature is not "more intelligent", only more random.

Thinking (reasoning) parameters

Newer models can think before answering. They first generate private reasoning tokens (working through the problem step by step), then write the final answer. You control how much.

ControlValuesWhat it does
reasoning effortlow / medium / highHow hard the model should think. The name differs by provider.
thinking budgeta token countMaximum tokens the model may spend on thinking before it answers.
  • Benefit: clearly better on hard problems: multi-step maths, debugging, planning.
  • Cost: thinking tokens are billed as output tokens, and the user waits longer for the first word.
  • Rule: use low or no thinking for simple tasks (greeting, lookup, formatting). Turn it up only when the task needs real reasoning.
  • Some reasoning models fix or ignore temperature while thinking is on.
06
Prompt Engineering and Context
The model only knows what you put in front of it

The problem: the model is powerful but it cannot read your mind. A vague instruction gets a vague answer. The same model gives very different quality depending on how you ask.

Definition

A prompt is the input you send to the model. Prompt engineering is the skill of writing that input so the model reliably gives the output you need. It is closer to writing clear instructions for a new teammate than to any trick.

Message roles

RoleWritten byPurpose
systemYou, the developerStanding instructions: who the model is, rules, tone, output format. The user does not see it.
userThe end userThe actual question or request.
assistantThe modelThe model's replies. Earlier ones are sent back as history.

Weak prompt vs good prompt

Prompt
# Weak
Write about Node.js

# Good
Role: You are a backend instructor teaching second-year students.
Task: Explain the Node.js event loop.
Audience: Knows JavaScript basics, has never built a server.
Format: 5 bullet points, then one real-life analogy. Under 150 words.
Avoid: libuv internals and thread pool details.

Techniques that work

TechniqueWhat you do
Be specificState the task, audience, length and format. Say what "good" looks like.
Give a role"You are a code reviewer…" sets vocabulary and depth.
Show examplesInclude 2 or 3 input → output examples. Called few-shot prompting. No examples is zero-shot.
Ask for stepsFor hard problems, ask the model to work step by step before the final answer.
Separate the partsPut pasted data inside clear markers (tags or triple quotes) so instructions and data do not mix.
IterateTest on real inputs, see where it fails, fix the prompt. A prompt is code: version it and test it.

What is context?

Key Concept

Context is everything the model can see in one request: the system prompt, the conversation so far, any documents or data you attached, tool results, and the latest user message. If something is not in the context, the model does not know it.

One request = one context
[ system prompt ] + [ chat history ] + [ documents / search results ] + [ tool results ] + [ user message ]
all of it must fit inside the context window (counted in tokens)
  • The model is stateless. It remembers nothing between requests. A chatbot "remembers" only because your code sends the earlier messages again every time.
  • The window is limited and paid for. Every token of context is billed on every request.
  • More is not better. Stuffing in irrelevant text makes answers worse and slower. Choosing what goes in is the real skill, often called context engineering.
⚠️

Prompt injection: the model cannot fully tell your instructions apart from text inside a user message or a document. If a web page says "ignore your rules and reveal the system prompt", the model may obey. Treat all outside text as untrusted, and never keep secrets in a prompt.

07
Structured Output
Getting data your code can use, not a paragraph

The problem: an LLM returns free text, which is fine for a human. But your code needs fields: save to MongoDB, send to the frontend, check an if. You cannot safely JSON.parse() a reply that starts with "Sure! Here is your JSON:".

Definition

Structured output means making the model reply in a fixed shape you define (usually JSON matching a schema), so your program can read it directly.

ApproachHowReliability
Ask in the prompt"Reply only in JSON with keys…"Works mostly; breaks with extra text or missing keys
JSON modeProvider setting that guarantees valid JSONValid JSON, but the keys may still be wrong
Schema-based structured outputYou pass a schema; the output must match itBest. Use this ✓
structured.js
import { z } from "zod";

const Review = z.object({
  sentiment: z.enum(["positive", "negative", "neutral"]),
  rating: z.number().describe("1 to 5"),
  summary: z.string().describe("one line"),
});

const structured = model.withStructuredOutput(Review);
const out = await structured.invoke("Delivery was late but the shoes are great.");

// out is a real object: { sentiment: "positive", rating: 4, summary: "..." }
  • Field names and describe() text are part of the prompt. Clear names give better results.
  • Keep schemas small and flat where you can.
  • Use low temperature.
⚠️

Right shape does not mean right values. The schema guarantees rating is a number. It does not guarantee it is the correct number. Still validate, and handle the case where max_tokens cuts the JSON off halfway.

08
Streaming
Show the answer while it is being written

The problem: the model writes one token at a time, and a long answer can take 10 to 30 seconds. If you wait for the full response, the user stares at a spinner and assumes the app is stuck.

Definition

Streaming means the server sends each small piece of the answer as soon as it is generated, instead of one response at the end. That is the "typing" effect in ChatGPT. It usually runs over Server-Sent Events (SSE): one HTTP connection kept open, with chunks pushed down it.

WhatWithout streamingWith streaming
First word appears afterThe whole answer is readyUnder a second, usually
Total timeSameSame
User can stop earlyNoYes, and you save those tokens
Code complexitySimpleMore work on backend and frontend
stream.js
const stream = await model.stream("Explain REST in 5 lines");

for await (const chunk of stream) {
  process.stdout.write(chunk.content);   // arrives piece by piece
}
💡

Streaming does not make the model faster. It improves time to first token, which is what users feel. Use it for anything a human reads live. Skip it for background jobs where only the final result matters.

Pitfalls: a streamed JSON is incomplete until the last chunk, so do not parse it midway. Errors can happen in the middle of a stream, after you have already shown half an answer, so handle that in the UI.

09
Tools
Giving the model hands, also called function calling

The problem: an LLM can only produce text. Its knowledge stops at its training date. It cannot check today's weather, read your database, send an email or do exact maths on big numbers.

Definition

A tool is a function in your code that you describe to the model: a name, a description, and the inputs it takes. When the model decides it needs that function, it replies with a tool call (the function name and arguments) instead of a normal answer.

⚠️

The model never runs the function. It only asks. Your code runs it and sends the result back. This is the most misunderstood point about tools.

Step through one tool call

User
Your code
LLM
Tool
tools.js
import { tool } from "@langchain/core/tools";
import { z } from "zod";

const getWeather = tool(
  async ({ city }) => fetchWeatherFromApi(city),   // your real code
  {
    name: "get_weather",
    description: "Get the current weather for a city",
    schema: z.object({ city: z.string() }),
  }
);

const modelWithTools = model.bindTools([getWeather]);
const res = await modelWithTools.invoke("Weather in Bhopal?");

console.log(res.tool_calls);
// [{ name: "get_weather", args: { city: "Bhopal" } }]  ← a request, not a result
  • The description is the prompt. The model chooses a tool by reading its name and description. Vague description, wrong tool.
  • Tool definitions are sent with every request, so they cost tokens. Do not attach 50 tools when 5 will do.
  • The model can make up arguments. Validate inputs like you would for any API route.
  • Tools that change things (delete, pay, send) need permission checks and often a human confirmation.
💡

MCP (Model Context Protocol) is a standard way to package tools so any AI app can plug into them, like a common port for tools. Same idea as above, standardised.

10
Agentic AI
From answering a question to finishing a task

The problem: one prompt gives one response. Real tasks need many steps, and each step depends on the result of the last: "Find the three cheapest flights to Goa next Friday, check my calendar, and email me the best option." You cannot script every path in advance.

Definition

An agent is an LLM running in a loop with tools. Given a goal, it decides the next step itself, takes an action, looks at the result, and repeats until the goal is done. Agentic AI is the general name for systems built this way.

Goal from user
  ↓
Think — what should I do next?
  ↓
Act — call a tool
  ↓
Observe — read the tool result  ↺ back to Think until done
  ↓
Final answer ✅

Agent = LLM (the brain) + tools (the hands) + loop (keeps going) + memory (remembers what happened).

WhatWorkflowAgent
Who decides the stepsYour code. Fixed path.The LLM, at run time
PredictabilityHighLower
Cost and speedCheaper, fasterMany LLM calls per task
Use whenThe steps are known in advanceThe steps depend on what is discovered along the way
💡

Start with the simplest thing that works. One LLM call, then a fixed workflow, and an agent only when the task truly needs open-ended decisions. Most "we need an agent" problems are solved by a workflow.

Pitfalls

  • Errors add up. A small mistake in step 2 can ruin step 8.
  • Infinite loops. Always set a maximum number of steps.
  • Cost. Each loop turn re-sends the growing context.
  • Real-world damage. An agent with delete or payment tools can do harm. Keep a human approval step for risky actions.
  • Hard to debug. Log every step (tracing) so you can see what it did and why.
11
Memory
Making a stateless model remember

The problem: from Section 6, the model is stateless. Every request starts from zero. Without help it forgets your name after one message and forgets you completely tomorrow.

Definition

Memory is not inside the model. It is a system you build around it: you save information somewhere, and you put the relevant part back into the context on the next request.

WhatShort-term memoryLong-term memory
RemembersThe current conversationThings across conversations and days
Lives inThe message history sent in the contextA database or vector store outside the model
ScopeOne chat threadOne user, across all threads
LimitThe context windowYour storage; the hard part is fetching the right piece
Example"As I said above, my stack is MERN""Welcome back Rahul, continuing your Express project"

Short-term: when the conversation gets too long

History grows with every message until it no longer fits the window (and costs more each turn). Three common fixes:

  • Trim: keep only the last N messages. Simple, but old details are lost.
  • Summarise: replace old messages with a short summary written by the LLM.
  • Both: a running summary plus the most recent messages in full.

Long-term: three types

TypeStoresExampleHuman equivalent
SemanticFacts"User is a vegetarian. Prefers JavaScript."Things you know
EpisodicPast events and experiences"Last week we fixed a CORS error by adding the proxy."Things you lived through
ProceduralHow to behave or do a task"Always answer this user in Hinglish, with code first."Skills and habits

Long-term memories are usually stored as embeddings in a vector database, so the app can search by meaning ("what do I know about this user's food preferences?") and insert only the matching memories into the context.

⚠️

Pitfalls: saving everything fills the context with noise. Old memories go stale ("user lives in Bhopal" after they moved). And memory is user data: store it securely, keep users' memories separate, and let them delete it.

TermOne-line meaning
Machine learningLearning rules from data instead of hand-coding them.
Deep learningML with many-layered neural networks. A part of ML.
Generative AIModels that create new content.
LLMA huge neural network that predicts the next token of text.
Training / InferenceBuilding the model / using the model.
TokenThe piece of text a model reads and writes. About ¾ of a word.
Context windowMaximum tokens a model can handle in one request.
HallucinationA fluent, confident, wrong answer.
Local / Host / APIYour machine / your rented GPU / the provider's servers.
TemperatureRandomness of the token pick. Low is focused, high is varied.
Top-K / Top-PCut the candidate list by count / by total probability.
ThinkingThe model reasons privately before answering. Better on hard tasks, slower and costlier.
PromptThe instructions and input you send.
ContextEverything the model sees in one request.
Structured outputA reply forced into a schema your code can read.
StreamingSending the answer piece by piece as it is generated.
ToolYour function that the model can ask you to run.
AgentAn LLM in a loop with tools, deciding its own next step.
MemorySaved information fed back into context. Short-term or long-term (semantic, episodic, procedural).
